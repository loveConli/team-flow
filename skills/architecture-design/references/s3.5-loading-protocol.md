# S3.5 产品级架构按域加载协议（v0.35.0，v0.14 §60.4）

> 产品级架构文档（iterations/vN/architecture.md + domains/）供变更级 architecture-design 子代理加载。
> 硬约束：单次上下文装载 ≤ **~2K token**（设计增强方案 v0.10 §29.1 三层策略）。本协议是 architecture-design SKILL.md「上下文加载协议」的产品级扩展。

## 三段式加载

| 段 | 内容 | 预算 |
|----|------|------|
| ① 索引层 | `docs/architecture/INDEX.md`（统计摘要）+ ARCHITECTURE.md §1-2（厚锚点：BC 表 + 聚合注册表） | ~400-600 |
| ② 按域加载（按需） | change 触及的 `domains/<bc>.md`（+ 相关 sequence/erd 片段） | ~800-1400 |
| ③ 变更增量 | `changes/<id>/architecture/` 增量 + 相关 changelog | ~200-400 |

## 加载规则

1. **先索引、后按域**：子代理先读 ① 索引层做路由（识别 change 触及哪些 BC），再按需加载 ② 该域的详细页。
2. **单域单次**：跨多域时一次只装载一个域文件，逐域分步处理（与 ch06 增量 SOP 对齐）。
3. **引用非复制**：只读不改；产品级聚合注册表是唯一事实源，change 内设计**引用**注册表 id，不重定义。
4. **迭代状态判定**（P1）：读快照还是读全局由迭代状态决定——
   - 迭代中（`snapshot_status: in-flight`）→ 读 `iterations/vN/` 快照（产品级决策权威）
   - 迭代收尾（`snapshot_status: superseded/archived`）→ 读全局当前态（唯一权威）

## 跨域降级（横向 change）

横向 change（跨 ≥3 个 BC 的公共组件改造）会突破单次预算。降级路径：

1. 只加载 ① 索引层 + 各域聚合注册表行（不加载详细页）。
2. 触及域按"受影响优先级"逐域分步处理（每步 ≤1 域）。
3. 加载前做 token 估算，超预算 → 告警 + 降级，而非硬约束失败。

## token 预算自动化校验

- 锚点（§1-2）与域页 token 预算加**自动化校验**（镜像 frontmatter-lint 模式，进 npm test）——不靠 LLM 自律。
- S3.5 产物自检 + S4 审计抽查：`iterations/vN/architecture.md` 的 §1-2 必须一句话级；`domains/<bc>.md` 单文件 ≤1500 token（超出继续拆子页）。

## 与既有加载协议的关系

- 本协议**扩展** architecture-design SKILL.md「上下文加载协议」，不替代（引用标题而非行号，防漂移）。
- 变更级 architecture-design 的输入 = 本协议 ① + ②（产品级）+ ③（变更增量）；语义层（五项检查判定、评审）仍走既有流程。
- S3.5 产品级评审门（architecture-reviewer product 视角 A1-A6）验证产物结构满足本协议（A1 结构完备 + A2 marker/锚点可解析），保证下游可按域加载。
